## 1. Classify what the handler does

The verb is a promise to clients, caches, proxies, crawlers and retry logic. A GET is assumed safe to prefetch, cache and retry; a PUT or DELETE is assumed safe to retry; a POST is not. So the check is: **what does this handler actually do, and does the verb promise match?**

Classify each handler into one of:

| Class | Evidence in the code |
|---|---|
| **read** | Only `find*`/`get*`/`exists*`/`count*` repository calls, queries, `@Transactional(readOnly = true)`, no external side effects. |
| **create** | `save()` of a new entity / `persist`, id generated by the server, a new row or resource appears. |
| **replace** | Loads by id, overwrites *all* client-editable fields from the body (absent fields become null/default), saves. |
| **partial update** | Loads by id, copies only fields present/non-null in the body, saves. |
| **delete** | `delete*`/`deleteById`, `@Modifying` delete query, or a soft delete flag (`deleted = true`, `deletedAt = now`). |
| **action** | A state transition or process that isn't plain CRUD: cancel, approve, send, recalculate, trigger a job. |

Trace the call chain — controller → service → repository / clients — until the classification is clear. Signals that state changes even though nothing is called "save":

- **JPA dirty checking:** inside a `@Transactional` method (non-readOnly), any setter on a managed entity loaded from a repository is flushed to the database at commit. A GET that calls `orderService.getDetails(id)` where the service does `order.setLastViewedAt(now())` *writes*.
- `@Modifying` repository queries, `JdbcTemplate.update`, `EntityManager.merge/remove`.
- Publishing events/messages (`KafkaTemplate.send`, `RabbitTemplate`, `ApplicationEventPublisher` with listeners that write), emails, SMS, webhooks, calls to other services' write endpoints, file writes, cache eviction that triggers recomputation with side effects.
- Counters and audit fields (view counts, `lastAccessedAt`) are the grey zone: they are writes, but often deliberate. Flag as a warning, not an error, and suggest moving them out of the request path (async event) or accepting it consciously.

If you cannot reach the implementation (interface with no implementation in the repo, external client), say so and classify as "unknown — depends on X".

## 2. What each verb promises

| Verb | Use for | Safe | Idempotent | Request body | Typical success |
|---|---|---|---|---|---|
| GET | Read a resource or collection | yes | yes | no | 200 + body |
| HEAD | Like GET, headers only (Spring MVC derives it from `@GetMapping` automatically) | yes | yes | no | 200 |
| POST | Create a subordinate resource with a server-chosen id; or run a non-idempotent action | no | no | yes | 201 + `Location` (create), 200/202/204 (action) |
| PUT | Replace the resource at a known URI with the full representation in the body (may create it if the client chooses the id) | no | yes | yes (full) | 200 + body or 204; 201 if it created |
| PATCH | Partially update the resource at a known URI | no | not necessarily | yes (partial) | 200 + body or 204 |
| DELETE | Remove the resource at the URI (hard or soft) | no | yes | no | 204 (or 200 + body) |
| OPTIONS | Capabilities/CORS preflight — handled by Spring, don't map manually | yes | yes | no | 200 |

**Idempotent** means repeating the same request leaves the server in the same state as doing it once (the response may differ — a second DELETE may return 404). This matters because clients, gateways and service meshes retry PUT/DELETE/GET automatically on timeouts.

## 3. Mismatch patterns to flag

**Errors** (dangerous today):
- **GET with side effects** — creates, updates, deletes or triggers actions (`GET /orders/{id}/cancel`, `GET /users/{id}/delete`, `GET /export` that emails a report). Browsers prefetch, crawlers and link previews follow links, caches and retries repeat it, and an `<img src>` on any site can fire it with the user's cookies (CSRF protection usually exempts GET). Spring MVC also answers HEAD by running the GET handler, so a HEAD request triggers the side effect too. Fix: move to POST (action) / DELETE / PATCH.
- **`@RequestMapping` with no `method`** on a handler — it answers *every* verb, so `DELETE /search` runs the search and `GET` on a write handler performs the write. Fix: use `@GetMapping`/`@PostMapping`/… (see `parameters.md`).
- **PUT that is not idempotent** — generates a new id or appends a row each call, increments a counter, or is mapped on a collection URI (`PUT /users`) to create. Fix: POST on the collection for server-generated ids.
- **PUT/PATCH data loss** — a PUT documented as "update" that merges non-null fields is fine as PATCH but then clients can never clear a field; a PATCH that copies every field (absent → null) wipes data clients didn't send. Fix: make PUT a true replace (validate the full representation) and PATCH a true partial update.

**Warnings** (wrong contract):
- **POST used to read** — `POST /users/list`, `POST /getOrders` with no or a trivial body. Reads should be GET with query parameters so they can be cached, bookmarked and retried. (Complex searches are an exception — see §4.)
- **POST used to update or delete a known resource** — `POST /users/{id}` that updates, `POST /users/{id}/delete`. Use PUT/PATCH/DELETE.
- **PATCH doing a full replace** or **PUT doing a partial merge** — name the actual behaviour and suggest the verb that matches, or change the implementation.
- **Request body on GET or DELETE** — HTTP gives it no defined meaning; many proxies, CDNs, clients (and some `RestTemplate`/`fetch` configurations) drop it. Move data to the path/query, or use POST for an action with a payload.
- **DELETE that isn't idempotent** — e.g. deletes "the latest item" rather than an identified resource.
- **Verb in the path duplicating the HTTP method** — `/getUser`, `/createOrder`, `/updateUser/{id}`, `/deleteUser/{id}`. Usually a symptom of the wrong verb; report together with the verb finding.

**Double submission of non-idempotent actions** (POST that moves money, advances a simulation, accepts an offer): check what a second identical request does, both sequentially (should be rejected or move on correctly — usually fine) and concurrently. Read-check-write with no `@Version`, no `@Lock`, and no unique constraint means two simultaneous requests both pass the check (Warning, "likely"). Where a "complete" step acts on a stored offer/order, also check it re-validates that the world still matches the offer (the seller still owns the item, the slot is still free) — two open offers on the same item can otherwise both complete (Error if it moves money).

**PATCH null vs absent:** a plain DTO cannot tell "field not sent" from "field sent as null". If the API must let clients clear fields via PATCH, it needs `JsonNullable` (openapitools), `Optional` wrappers, a `Map`/`JsonNode` body, or JSON Merge Patch (`application/merge-patch+json`). Flag as a warning when PATCH copies only non-null fields and the domain has nullable fields that clients may need to clear.

## 4. Legitimate exceptions (don't flag, or flag only as a suggestion)

- **Action sub-resources via POST**: `POST /orders/{id}/cancel`, `POST /payments/{id}/refunds`, `POST /users/{id}/activation`. A state transition that isn't a field edit is fine as POST on a sub-resource (noun forms like `/cancellation` are a style choice, not a defect).
- **Search via POST** when the filter is too large or structured for a query string (`POST /orders/search` with nested criteria). Acceptable; a suggestion at most (note it isn't cacheable).
- **Upserts via PUT** where the client supplies the id (`PUT /devices/{serial}`) — correct use of PUT, returning 201 on create and 200/204 on update.
- **Soft delete via DELETE** — still a delete from the client's point of view.
- **Batch operations** (`POST /orders/batch`) — acceptable as POST.
- **GraphQL, RPC-style or webhook receiver endpoints** — not REST; don't apply resource-verb rules, only safety rules.
- Project rules that mandate a pattern.

## 5. Status codes

| Situation | Expected |
|---|---|
| GET single resource found | 200 |
| GET single resource missing | 404 (not 200 with `null`/empty body, not 500) |
| GET collection, nothing matches | 200 with `[]` / empty page (not 404) |
| POST created | 201 Created + `Location: /orders/{newId}` header, usually the created body |
| POST accepted for async processing | 202 Accepted (+ a status URL) |
| POST action, no content | 204, or 200 with a result body |
| PUT replaced / PATCH updated | 200 with body, or 204 |
| PUT created (client-chosen id) | 201 |
| DELETE | 204 (200 if it returns a body); missing resource: 404 or 204 — either is fine, but be consistent across the API |
| Validation / malformed input | 400 (422 if the project uses it consistently) |
| Unauthenticated / forbidden | 401 / 403 |
| Conflict (duplicate, version mismatch, invalid state transition) | 409 (412 for failed `If-Match`) |
| Unsupported verb on an existing path | 405 — Spring does this automatically when mappings are verb-specific |
| Unsupported media type / not acceptable | 415 / 406 — Spring automatic |
| Unexpected server error | 500, with no stack trace or internal message in the body |

In Spring: a handler returning a plain object always yields 200 unless `@ResponseStatus(HttpStatus.CREATED)` or `ResponseEntity` says otherwise. Check create handlers specifically — returning `ResponseEntity.ok(saved)` or a bare object from a POST that creates is the most common status-code finding. `Location` is easiest via `ResponseEntity.created(ServletUriComponentsBuilder.fromCurrentRequest().path("/{id}").buildAndExpand(id).toUri())`.

## 6. URI design

Check against the project's existing style first; these are defaults when there is none.

- **Nouns, plural, for collections**: `/orders`, `/orders/{orderId}`, `/orders/{orderId}/items`. No verbs for CRUD (the verb is the HTTP method).
- **Lowercase, kebab-case** segments: `/order-items`, not `/orderItems` or `/order_items`. Path matching is case-sensitive, so mixed case breaks clients that guess.
- **Identifiers in the path, filters/sort/paging in the query**: `/orders?status=OPEN&page=0&size=20`, not `/orders/open/page/0`.
- **Shallow nesting**: at most resource/sub-resource (`/customers/{id}/orders`); deeper chains (`/customers/{c}/orders/{o}/items/{i}/notes`) suggest a top-level resource.
- **No trailing slash, no file extensions** (`/orders.json`). Spring 6 no longer matches `/orders/` to `/orders` by default.
- **Consistent prefix and versioning** across controllers (`/api/v1/...`), defined once (class-level `@RequestMapping` or `configurePathMatch`), not repeated by hand in every method.
- **Consistent id naming** in templates (`{orderId}` vs `{id}`) within a controller.
